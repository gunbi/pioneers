# 架构设计

1. 明确用户路径、当前约束和真正的复杂度来源。根据项目需要考虑性能、可用性、扩展性、安全、规模和成本。记录已有证据，标出仍待验证的假设。
2. 先写出能满足约束的最简方案。跨模块或高复杂度任务再比较可行的备选方案，说明收益、引入的复杂度、成本和落地难度。记录选型理由，以及什么变化值得重新评估。
3. 定义模块职责、依赖方向、状态归属和持久化边界。跨端协作时明确请求字段、成功响应、错误行为和兼容要求。涉及重试或数据同步时，约定重复请求与读到旧数据时的行为。让各方能基于同一契约编写实现、Mock 和测试。
4. 按任务复杂度交付。轻量改动写清边界、接口和验证方式。复杂任务补上备选方案、关键流程、失败场景和演进条件。出现性能、数据一致性或可用性问题时，再读取同目录的 [性能、存储与可用性](references/performance-storage-reliability.md)。
5. 如果任务要求结构化交付，提供 `architecture.json` 或等价的结构化内容。至少包含 `summary`、`modules`（每项有 `name` 和 `responsibility`）及 `interfaces`（每项有 `name` 和 `contract`，无跨模块接口时可为空数组）。在已有文件可读的情况下，用 `architecture_check` 检查结构。对实际行为的验收使用项目测试。
